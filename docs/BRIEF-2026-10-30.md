# One Authenticator — Codex Development Brief

**Product:** One Workspace
**Application name:** One Authenticator
**Suggested repository:** `one-authenticator` in the existing One Workspace GitHub organisation (verify the actual organisation before creating it)
**Target:** Self-hosted Windows server + installable offline-capable mobile/web authenticator
**Distribution:** Single portable Windows `.exe` for the web-app host, with bundled static assets and no Docker requirement
**Status:** Development specification — not an implementation or security certification
**Date:** 30 October 2026

---

## 1. Mission

Build **One Authenticator**, a small, attractive authenticator app **solely for OneAccount**, the identity and single sign-on service for the One Workspace ecosystem.

When a user signs in to OneAccount, they enter their username/password, then a **six-digit, time-based one-time password (TOTP)** generated by One Authenticator. Codes refresh every **30 seconds**. The authenticator should continue generating codes **without internet access** after initial setup.

The app is **not** a general Google/Microsoft Authenticator clone. It should **not** support adding Google, GitHub, Microsoft, banking, or other third-party accounts in the first release.

**Architectural principle:** OneAccount remains the **server-side source of truth for MFA enrolment, credential state, code verification, recovery and sessions**. One Authenticator is the **independent, local code generator**. Do not build another authentication database or a competing identity system.

## 2. Success criteria

1. A OneAccount user can enrol a phone by scanning a QR code displayed under **OneAccount → Security → Two-factor authentication**.
2. The phone displays a working six-digit code with a 30-second circular countdown, including while offline.
3. An enrolled OneAccount user cannot access One Workspace apps with only their password; OneAccount requires an MFA challenge before issuing a fully authenticated SSO session.
4. Reusing the same TOTP within its accepted validity step is rejected.
5. A user can recover from a lost phone using one-time recovery codes; enrolment, removal and recovery are appropriately authenticated and audited.
6. Users cannot get trapped in a circular flow where they must sign in to OneAccount to see their OneAccount sign-in code.
7. The web-app host packages into a portable `.exe` on Windows, with no Docker, and its PWA can be installed on a phone.
8. No TOTP secret is exposed to third-party telemetry, logs, ordinary cloud storage, or unprotected application APIs.

## 3. Required user experience

### 3.1 OneAccount setup (desktop)

1. User signs in to an existing OneAccount session.
2. Navigates to **Profile / Account Settings → Security → Two-factor authentication**.
3. Clicks **Enable two-factor authentication**.
4. OneAccount performs a recent-authentication / step-up check before starting enrolment.
5. OneAccount creates a *pending*, short-lived secret for this user and displays a QR code, along with a collapsible **Enter setup key manually** option.
6. The screen explains: **Open One Authenticator on your phone → Add OneAccount → Scan QR code**.
7. User scans QR code. The authenticator creates an encrypted local entry and displays the code.
8. User enters the six-digit code into OneAccount. OneAccount validates it and **only then** activates MFA on the account.
9. OneAccount generates and shows **10 one-time recovery codes**; user is instructed to save them separately from the phone.
10. OneAccount shows **2FA enabled**, enrolment date, associated device label, and recovery-code status.

If verification fails or the user cancels, the pending secret expires and is not enabled. Never make MFA active just because a QR code was displayed.

### 3.2 OneAccount login

1. User enters OneAccount username/password.
2. Server validates password but creates only a **short-lived, limited pre-MFA challenge** — not a normal app/SSO session.
3. Login UI shows **Enter the 6-digit code from One Authenticator**.
4. User opens One Authenticator, unlocks their **local vault** if required, and enters the code.
5. OneAccount checks the OTP on the server with strict limits, anti-replay tracking, and an atomic success transition.
6. Only after success is the fully authenticated OneAccount session / SSO token established, allowing access to My Drive, My Office, My Photos and other One Workspace applications.
7. Provide a discreet **Use a recovery code** option.

The required-MFA condition must be enforced centrally by OneAccount. Do not rely on front-end redirects or individual app checks. All app, refresh-token, API and SSO paths must respect the completed-MFA state.

### 3.3 The One Authenticator app

A minimal, polished, mobile-first One Workspace-branded interface:

- Logo + title: **One Authenticator**.
- Account label: **OneAccount** and a masked account identifier or display name.
- Large, legible six-digit code: `123 456` (illustrative only).
- Circular countdown and progress animation over 30 seconds.
- **Tap to copy** button; auto-clear clipboard after a short interval where technically supported (do not promise clearing beyond platform guarantees).
- Small **Works offline** status when disconnected.
- Local vault **Lock / Unlock**.
- **Settings**: device label, lock preference, enrolment help, clock/time troubleshooting, remove local account with confirmation, app version.
- Accessible, responsive layouts; keyboard support, high contrast and screen-reader labels.
- Never show irrelevant third-party account import or add-service flows.

**Proposed screens:** Welcome / Install; Scan QR / Enter Key; Code Screen; Local Vault Unlock; Settings; Lost Device Help.

### 3.4 Independence from OneAccount login

**Critical:** One Authenticator must be usable *without a current OneAccount login, network connection, or access to the OneAccount server*. The mobile app/PWA must use a **local encrypted secret** provisioned at setup. Protect access with an **independent local unlock method**.

Do not fetch the TOTP seed from OneAccount each time a code is required. Do not store the local vault decryption key in a OneAccount session cookie. A user must be able to open the already-installed authenticator during a OneAccount outage or login challenge.

## 4. Technical architecture

### 4.1 Component boundaries

**A. OneAccount server (modify/integrate existing code)**

- Create/manage pending enrolments.
- Store active MFA credential secrets **encrypted at rest**, with keys stored separately and tightly protected.
- Validate TOTP codes, enforce anti-replay rules and throttling.
- Manage recovery-code hashes, device enrolments and administrative MFA policy.
- Require MFA before final authentication and SSO issuance.
- Audit critical security events.

**B. One Authenticator portable Windows service**

- Prefer **Go** for a single Windows `.exe`, embedding the compiled React/TypeScript/Vite static PWA (`go:embed` or equivalent).
- Serve the installation guide, icons, manifest and offline-capable application assets, using the existing One Workspace HTTPS/reverse proxy/Cloudflare Tunnel conventions.
- No Docker, external database or third-party hosted runtime.
- The public PWA bootstrap must **not** require OneAccount authentication; it serves code and UI assets, not secrets.
- Where practical, serve under a scoped origin/path such as `authenticator.<configured-domain>` (or a carefully scoped `/authenticator/` path) without interfering with OneAccount login or its service workers.
- Expose only necessary health/version endpoints; never expose secrets, server verification routines or account admin functions from this host.

**C. Installed mobile PWA (primary user code generator)**

- Responsive React/TypeScript app with a web app manifest, install prompts, offline application shell and versioned service-worker caching.
- Camera QR scanning on supported HTTPS browsers, plus manual setup-key entry.
- Local TOTP generation via audited, standards-conformant primitives; use the Web Crypto API where appropriate.
- Encrypt the seed at rest on the device, only unlocking locally; do not put secrets into URLs, analytics, service-worker caches, log output, or plain localStorage.
- Persist the encrypted vault using IndexedDB or an appropriate supported device store.
- Warn that clearing browser/site data or uninstalling the PWA may delete the local vault; recovery codes are essential.
- A native Android/iOS companion with OS Keychain/Keystore-backed protection is a **future hardening path**, not a requirement for v1. Document PWA storage, browser and biometric limitations accurately.

### 4.2 Security-conscious local unlock

Use a **vault passphrase** with a reputable memory-hard KDF (e.g. Argon2id, with measured parameters) and authenticated encryption (e.g. AES-256-GCM). If a convenience PIN is offered, do **not** present a short PIN plus browser storage as equivalent to hardware-backed protection; offline attackers can extract encrypted storage and attempt guesses. Use hardware-backed OS key protection if/when a native companion is built. A locked vault must not reveal TOTP seeds or active codes.

Biometric unlocking may only be presented when a real platform-supported, appropriately protected local-unlock implementation is available. Do not put a fake biometric button in the shipped UI.

### 4.3 Security boundaries and storage

- OneAccount never relies on the *web app host* to decide whether a TOTP is correct.
- OneAccount database is authoritative for enabled/disabled/recovery state. Use existing account IDs and DB migrations. **Inspect actual OneAccount code and schema first**; do not assume specific API routes, cookie format, ORM or DB engine.
- One Authenticator owns only its local device vault and its static web assets.
- Do **not** automatically synchronise TOTP seeds or backup codes into My Drive. If secure, user-controlled vault transfer is later added, it requires separate threat modelling and end-to-end encrypted backup with user-held keys.
- Authentication and MFA-verification endpoints must be HTTPS-only on remote access.
- Handle the server master/envelope-encryption key via an existing secure secret-management mechanism. Never hardcode it or commit it to source control.

## 5. TOTP protocol and verification

Implement **RFC 6238** using commonly interoperable values:

| Parameter | Requirement |
|---|---|
| Code type | Time-based one-time password (TOTP) |
| Code length | Six numeric digits; retain leading zeros |
| Period | 30 seconds |
| Hash | HMAC-SHA-1 for baseline authenticator interoperability; SHA-1 here is part of standardized HMAC-based TOTP, not for password hashing |
| Shared secret | Cryptographically secure random secret, minimum 160 bits, unique per enrolment/credential |
| QR format | Standard `otpauth://totp/...` provisioning URI |
| Issuer | `OneAccount` |
| Account label | Actual OneAccount identifier, appropriately encoded |
| Validation | Server-side; exact account/credential binding; reject replays |
| Clock tolerance | Narrow, documented skew window (normally current step ±1); never silently accept broad windows |

Use a tested library if its maintenance, license and security properties are acceptable; still validate against RFC test vectors. Never write a custom crypto algorithm. Treat QR content and manual setup keys as **sensitive secrets**.

**Replay prevention:** Track consumed time steps per TOTP credential (or otherwise reliably prevent reuse) and make verification + consumption atomic across concurrent login requests. Account for allowed adjacent time windows without accepting an already-used code. Constant-time comparisons should be used where applicable.

**Rate limiting:** Apply limits per user/account, pre-MFA challenge and IP/device risk context; include backoff and safe error messages. Changing IP or creating a new challenge must not reset account-wide guessing protection. Review abuse, lockout and denial-of-service tradeoffs.

## 6. Security and account recovery

### 6.1 Recovery codes

- On enrolment issue **10 independent high-entropy, single-use recovery codes** using a CSPRNG; codes must have enough entropy to resist online guessing and accidental predictability.
- Show once; allow a deliberate print/download action accompanied by a storage warning.
- Store only keyed cryptographic digests or otherwise safely hashed representations on OneAccount, not raw recovery codes.
- Use and invalidate each recovery code atomically; audit attempts and success; apply rate limits.
- Allow regeneration only after successful recent-authentication/step-up, which invalidates the old set.
- Recovery codes should not silently disable MFA or give a permanent bypass. After an account recovery, prompt secure replacement device enrolment.

### 6.2 Lost-device workflow

- Login challenge provides **Use a recovery code**.
- After successful recovery, allow access to **Security → Replace authenticator** with appropriate extra verification and notification.
- Revoke old credentials deliberately, enrol a new device, and rotate recovery codes where appropriate.
- If all codes are lost, do **not** implement an unauthenticated email-only bypass. Design a documented, high-assurance owner/admin-assisted recovery process based on the existing OneAccount governance model, with delays/notifications where appropriate.
- Send a security notification upon enrolment, disablement, recovery-code use or authenticator replacement, without exposing secrets.

### 6.3 Account management

- Show MFA status, enrolled device labels and last-used metadata (where supportable), without exposing secrets.
- Support more than one **independently enrolled OneAccount authenticator device** if the current OneAccount architecture allows it. Each device gets a unique seed and its own replay-tracking state. Never clone the same secret by default.
- Removing a device, disabling MFA, regenerating recovery codes or adding another device requires recent password reauthentication plus current MFA/recovery proof (or a documented equivalent step-up).
- Invalidate/review existing sessions after high-risk security changes according to policy.
- Offer optional organisation-level **MFA required** policy, but never enable this for all existing users without a safe migration and recovery plan.

### 6.4 Threats that must be explicitly tested

Password-only SSO bypass; leaked provisioning QR; phishing or real-time relay (TOTP is **not phishing-resistant**); brute-force guessing; TOTP replay; concurrent request replay; MFA downgrade or disablement; CSRF; account enumeration; stolen browser storage; clock drift; browser storage eviction; recovery-code reuse; lost phone; master-key disclosure; unprotected backup; PWA cache poisoning; service-worker scope collisions; malicious extensions; proxy and reverse-proxy header misconfiguration; localhost-to-public exposure.

## 7. OneAccount integration contract

Before coding, Codex must **find and inspect the current OneAccount repository**, authentication handlers, SSO model, token issuance, middleware, database, encryption/key-management conventions and existing security settings.

Treat the following as **conceptual operations**, not predefined routes. Implement in the project's existing conventions:

- `beginMfaEnrolment(recentlyAuthenticatedSession)` → short-lived pending QR/manual-key provisioning data.
- `confirmMfaEnrolment(pendingEnrolment, otp)` → activates MFA and issues recovery codes.
- `beginMfaChallenge(passwordVerifiedContext)` → limited pre-auth challenge only.
- `verifyMfaChallenge(preAuthChallenge, otpOrRecoveryCode)` → full OneAccount session only after valid MFA.
- `listMfaDevices()`, `addMfaDevice()`, `removeMfaDevice()`, `regenerateRecoveryCodes()`, `disableMfa()` → step-up protected.

Enforce MFA at **the central SSO/token-issuance boundary** for every One Workspace application, including My Drive, My Office, My Photos and future apps. Existing active users and tokens require a deliberate migration/transition policy. Do not invent routes and claim they already exist; document the actual implemented paths after inspecting the repository.

## 9. Build, packaging and deployment

- Confirm actual repository and service structure, supported Windows version, service ports, process model and One Workspace deployment scripts.
- Build reproducibly with a locked dependency graph and an auditable source/release history.
- `one-authenticator.exe` must embed its web assets and start without requiring Node.js, Go, Docker, or a separately installed database on the end-user machine.
- Reuse existing Windows BAT/PowerShell startup/install conventions, configurable local port, persistent data/config paths, app version and health endpoint.
- Bind to loopback by default unless deliberately configured behind the existing trusted reverse proxy/tunnel. Do not expose debug/admin endpoints publicly.
- Remote PWA access and camera functionality require a correctly configured **secure HTTPS origin**. Document public-domain/tunnel configuration without hardcoding the user's domain.
- The PWA must remain usable offline **after the app has been installed and successfully provisioned**. The host EXE does not need to be running to generate already-provisioned codes on the phone.
- Release README should include mobile PWA installation steps (Android and iPhone), backup guidance, common clock problems and how to replace a lost phone.
- Package Windows executable, config example, checksums, release notes and upgrade instructions.

## 10. Testing and verification

Do not claim successful MFA implementation on UI behaviour alone. Write and run automated tests that exercise the **actual OneAccount login/SSO server**.

**Unit tests**

- RFC 6238 test vectors; leading-zero codes; period rollover and edge timestamps.
- Enrollment creation/expiry/confirm/cancel and invalid QR/manual keys.
- Device-specific secrets, multiple devices, replay and allowed clock skew.
- Recovery code generation, hashing, consumption and regeneration.
- Encrypted vault locked/unlocked lifecycle, storage corruption, wrong passphrase, time drift.

**Integration and adversarial tests**

- Password-only login cannot obtain privileged session or call protected APIs.
- Valid OTP succeeds; invalid OTP fails; expired OTP fails; same OTP replay fails; concurrent reuse fails.
- Valid recovery code succeeds only once and is audited.
- Direct access to individual One Workspace app SSO entrypoints cannot bypass MFA.
- Editing client-side cookies, URL parameters or UI state cannot manufacture an MFA-complete session.
- Existing sessions and refresh tokens follow the chosen MFA-transition policy.
- QR scanner works with camera permission; manual key fallback works.
- With phone in airplane mode and server offline, previously provisioned vault can be unlocked and produces locally correct codes.
- Enrolment cannot leave a user permanently locked out when interrupted.
- Existing OneAccount users without enrolled MFA still have the documented migration path.
- Security endpoints are protected against CSRF, rate-limit bypass, credential disclosure and account enumeration.

**Real-device testing:** test on at least one Android Chrome PWA and one supported iPhone/Safari PWA if available, documenting untested devices honestly. Local Windows test installation is preferred; no VM is necessary as a project prerequisite. Use only test accounts and test secrets in automated tests. Avoid changing real production identity policy without an explicit deployment decision.

## 11. Phased implementation plan

**Phase 0 — Repository discovery and security design**
Inspect the actual OneAccount integration points and existing One Workspace patterns. Produce a concise architecture and threat model; identify blockers, applicable database migrations and migration safety.

**Phase 1 — OneAccount server-side MFA**
Implement pending enrolment, TOTP verification, pre-MFA session state, anti-replay, rate limiting, recovery codes and settings. Build focused tests before exposing UI.

**Phase 2 — One Authenticator mobile PWA**
Implement QR scanner/manual entry, encrypted local vault, offline generation, lock/unlock and polished UI. Verify browser/device lifecycle behaviour.

**Phase 3 — End-to-end SSO enforcement**
Integrate OneAccount login, recovery and central session/token issuance across One Workspace. Audit direct API and refresh-token bypasses.

**Phase 4 — Windows `.exe`, local tests and release**
Embed assets, compile portable Windows executable, verify installed mobile PWA and full login cycle. Write setup docs, run build/security tests, push reviewed source to the verified One Workspace organisation and publish a versioned release after passing checks.

## 12. Non-goals for v1

- Acting as a multi-service Google/Microsoft Authenticator replacement.
- Password manager or storing OneAccount passwords.
- Push notifications, approve/deny prompts or Microsoft Authenticator number matching.
- Importing/exporting external account QR codes.
- SMS/email OTP as an equal-strength alternative to the app.
- Cloud synchronisation of raw TOTP secrets or automatic My Drive backup.
- Mandatory native iOS/Android app distribution.
- Major redesign/replacement of OneAccount itself.
